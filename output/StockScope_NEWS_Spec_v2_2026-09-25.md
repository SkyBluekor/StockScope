# StockScope 뉴스 분석과 주가 방향 예측 작업 명세

버전 2.0 · 2026년 9월 25일 · 구현 및 검증 담당 채팅에 전달할 기준 문서

## 1 제품 목표와 필수 결정

StockScope는 사용자가 직접 데이터를 조합하고 해석하는 부담을 줄인다. 기업과 업종, 정책, 국제 정세, 시장의 기대와 불안에 관한 정보를 종목에 연결하고, 예상 주가 방향과 기간, 핵심 이유를 짧게 제공한다. 뉴스 목록을 표시하는 것은 기반 작업이며, 최종 목표는 근거를 검증한 주가 방향 예측이다.

사용자는 첫 화면에서 어느 종목이 어느 방향으로 어느 기간에 움직일 가능성이 있는지 파악해야 한다. 상세 통계나 기사 전문을 읽어야만 결론을 알 수 있는 화면은 목표에 맞지 않는다. 정보 부족도 시스템이 판단해 이유와 함께 명확하게 표시한다.

### 반드시 반영할 사용자 요구

- 기업명으로 검색한 뉴스 외에 업종, 경쟁사, 고객사, 공급망, 국가 정책, 국제 분쟁, 금리·환율·원자재, 관심과 불안을 움직이는 소식을 포함한다.
- 계약·공급·실적 사건에만 범위를 한정하지 않는다. 사실 변화가 확인되기 전의 기대와 우려도 관찰하되, 확정 사실과 구분한다.
- 단순한 사업 영향 설명을 넘어 종목별 예상 주가 방향을 제공한다. 현재 가격 반응과 과거 유사 사례를 함께 고려한다.
- 보유 종목을 우선 표시하지만, 선택한 종목·관심 종목·관련된 미보유 종목도 분석 대상이다.
- 기사 전문을 수집하거나 내부에서 펼쳐 보여주지 않는다. 제목을 누르면 원문이 새 탭으로 열린다.
- 화면의 기본 단위는 뉴스 제목, 짧은 내용, 관련 종목, 예상 방향과 기간, 핵심 이유다.
- 문장은 성인 사용자를 존중하는 담백한 설명체로 쓴다. 전문용어는 줄이되 의미와 불확실성을 생략하지 않는다.
- Secret은 backend에만 둔다. 뉴스와 예측 장애는 기존 종목 분석을 중단시키지 않는다.

### 완료의 의미

NEWS.1은 연결과 표시 기반의 완료를 뜻한다. 전체 뉴스 분석 기능은 여러 범위의 사건을 종목에 연결하고, 과거 자료로 검증한 예측을 실제 화면에 제공해야 완료다. 데이터 권한이나 검증 성능이 부족하면 그 부분을 미완료로 기록한다. 화면을 그럴듯하게 채우기 위해 임의의 예측·확률·과거 통계를 생성하지 않는다.

이 문서는 작업 명세다. PR 병합, 브랜치 생성, 서비스 구현, 실제 키 검증을 완료했다는 보고가 아니다. 다음 담당자는 작업 시작 요청을 받으면 13장의 순서로 실행한다.

### 저장소 확인 사항

문서 작성 시 로컬 checkout은 main, HEAD는 3b4b052였다. 이 값은 당시 스냅샷이며 최신 원격 main이나 PR #5 상태를 뜻하지 않는다. 구현 시작 시 다시 확인한다.

- .env.example에는 NAVER_CLIENT_ID와 NAVER_CLIENT_SECRET이 있다. 새 표준 이름으로 전환하고 예제에는 빈 값만 남긴다. 실제 .env 값은 이 문서 작성 중 열람하거나 검증하지 않았다.
- backend/app/core/config.py는 project-root .env를 지정한다. 새 Settings 필드도 이 경로를 따른다. 운영체제 환경변수 우선순위는 기존 Settings 동작을 유지한다.
- frontend/src/App.tsx의 quickAnalyze가 현재 stock context를 조회한다. 종목 선택만으로 기본 context와 뉴스가 로딩되는 흐름을 별도로 구현해야 한다.
- backend/app/market/service.py의 stock_context는 KRX와 OpenDART를 호출한다. 뉴스 조회마다 이 함수를 다시 실행해 회사명을 얻는 구조를 만들지 않는다.
- .github/workflows/ci.yml에는 Frontend Node 22와 Backend Python 3.11·3.14 검증이 있다. 모든 필수 job의 성공을 확인한다.

## 3 화면과 문장 설계

### 종목 분석 화면

종목 선택 후 기본 context와 뉴스를 독립적으로 불러온다. 사용자가 보는 주가 예측은 선택한 종목을 기준으로 작성한다. 상단의 종목 판단 근처에 검증된 뉴스 기반 예상 한 줄을 연결하고, 기업 분석 아래의 최근 뉴스 목록에 근거가 된 소식을 배치한다. 같은 결론을 긴 카드 여러 개로 반복하지 않는다.

화면 순서는 신규 진입 판단, 가격 계획과 차트, 판단 이유, 기술적 상태, 기업 분석, 최근 뉴스, 투자 관점별 분석, 참고 시나리오, 전문 분석을 기본으로 유지한다. 뉴스 기반 예측은 기존 전략 결과와 근거·시각이 다른 경우 이를 짧게 설명한다. 합산한 새 전략 점수를 임의로 만들지 않는다.

### 뉴스 한 건의 기본 구성

| 요소 | 화면 계약 |
| --- | --- |
| 제목 | 원문 링크. target=_blank 및 rel=noopener noreferrer. 제목 옆 상승·하락 색상은 사용하지 않는다. |
| 짧은 내용 | 확인된 사실을 1~2문장, 모바일 기준 약 2~3줄로 표시한다. 제공 설명 또는 가공 권한이 있는 요약만 사용한다. |
| 주가 예상 | 관련 종목명, 상승·하락·큰 변화 없음·판단 어려움 중 해당 상태, 명확한 예상 기간을 제공한다. |
| 핵심 이유 | 해당 회사와의 관계, 현재 반응 또는 검증된 과거 근거 중 중요한 내용을 1~2문장으로 설명한다. |
| 시각과 출처 | 출처, 뉴스 제공 또는 발표 시각, 예측 기준 시각을 구분해 작게 표시한다. 출처명이 없으면 확인된 원문 도메인을 쓴다. |
| 원문 | 내부 기사 전문 보기·본문 펼치기·무단 본문 수집을 구현하지 않는다. 링크로 이동한다. |

허용된 분석 자료로 묶은 사건은 대표 소식 하나와 관련 종목을 함께 보여준다. 원본 검색결과의 순서나 내용을 유지해야 하는 provider는 별도의 출처 표시 목록으로 제공하고, 임의 재정렬·예측 삽입을 하지 않는다. 최종 통합 화면은 해당 사용 권한이 확보된 자료로 구성한다.

### 문구 예시

다음은 형식 설명을 위한 가상 예시이며 실제 분석 결과가 아니다.

원유 공급 차질 우려 확대

주요 산유 지역의 긴장으로 원유 공급이 줄어들 가능성이 제기됐습니다.

A항공 — 단기 하락 가능성이 우세합니다. 예상 기간은 다음 5거래일입니다.

연료비 부담 증가 가능성과 현재 가격 움직임을 함께 반영했습니다. 비슷한 과거 사례의 결과도 같은 방향을 뒷받침합니다.

위와 같은 과거 근거 문장은 실제 검증 자료가 있을 때만 출력한다. 근거가 부족하면 “단기 방향을 판단하기 어렵습니다. 정책 적용 대상이 아직 확정되지 않았습니다”처럼 이유를 구체적으로 쓴다. 큰 변화 없음은 검증된 가격 범위 안에 머물 것으로 보는 예측이며, 판단 어려움과 구분한다.

“큰 계약을 따냈어요”, “걱정되는 소식이에요”, “쉽게 말해”처럼 가볍거나 가르치는 말투를 피한다. “신규 공급계약이 체결됐습니다”, “매출 증가가 예상됩니다”, “이익에 미치는 영향은 아직 확인되지 않았습니다”처럼 쓴다. 확정·예상·우려를 같은 사실 수준으로 표현하지 않는다.

## 4 뉴스 범위와 데이터 사용 권한

### 분석 대상 범위

| 범위 | 예시 | 종목 연결 근거 |
| --- | --- | --- |
| 기업 | 실적, 계약, 제품, 경영진, 사고, 자사주, 자금 조달 | 해당 법인, 제품, 사업, 자회사와의 확인된 관계 |
| 업종과 사업 관계 | 경쟁사 실적, 고객 투자, 공급 부족, 기술 변화 | 업종, 고객·공급사, 제품 시장, 대체 가능성 |
| 국내 정책 | 지원금, 세제, 규제, 인허가, 산업 정책 | 적용 품목·지역·시행일과 기업의 해당 여부 |
| 국제 정세 | 분쟁, 관세, 수출 제한, 제재, 해상 운송 차질 | 판매 지역, 공장 위치, 조달 경로, 물류비 |
| 시장 환경 | 금리, 환율, 원유, 원자재, 경기 지표 | 차입 구조, 통화, 원가, 수요, 시장 공통 영향 |
| 관심과 심리 | 산업 기대, 유명 인사 발언, 우려 확산, 소문 | 기사·관심 지표의 실제 관측과 기업 관련 근거 |

회사명을 언급하지 않는 기사도 위 관계가 입증되면 대상에 포함한다. 같은 사건이 같은 업종의 모든 기업에 동일한 방향으로 작용한다고 가정하지 않는다. 업종 이름만 같은 경우에는 관련성 근거를 낮게 평가한다.

### 제공 경로별 권한 확인

네이버 개발자센터의 2026년 9월 7일 개정 약관은 검색결과의 독립 표시, 가공·순위 변경 제한, AI 입력과 활용 제한, 목적별 임시 보관 조건을 명시한다. 따라서 검색결과를 임의로 AI에 전달하거나, 파생 데이터를 영구 보관하거나, 분석 카드에 섞는 권한이 있다고 가정하지 않는다. NAVER API HUB의 실제 적용 약관과 개별 계약은 별도로 확인한다. [S1]

구현 전 source별 display_allowed, transform_allowed, ai_allowed, retention_policy, attribution_required를 기록한다. 미확인 항목은 허용으로 간주하지 않는다. HTML 표시 처리, 중복 제거, 임베딩, 감성 분석, 사건 추출, 요약과 재배열도 사용 목적에 포함해 확인한다. 제한된 자료를 다른 이름의 중간 파일로 저장하거나 외부 AI로 보내는 우회는 금지한다.

네이버 검색은 허용 범위의 제목·설명·원문 링크 제공에 사용한다. 주가 예측용 사건 자료는 AI 분석과 필요한 보관이 허용된 뉴스 계약, 공식 공시·정책 발표 등에서 확보한다. 공식 자료도 자동으로 모든 활용이 허용된다고 가정하지 않고 조건을 확인한다. 기사 전문 크롤링은 이 작업의 범위에 포함하지 않는다.

### 제공 시스템과 시각의 확인

기존 개발자센터 검색 API와 API HUB는 endpoint와 인증 헤더가 다르다. 기존 키의 지원 종료 공지는 2027년 6월 30일을 명시한다. 새 provider는 발급 플랫폼을 설정으로 구분하고 해당 인증 규약만 적용한다. 두 플랫폼에 Secret을 번갈아 전송해 종류를 추측하지 않는다. [S2, S3]

검색 응답의 description은 발췌문이며 기사 전문을 읽었다고 표시하지 않는다. pubDate는 네이버 제공 시각일 수 있다. source_published_at, provider_published_at, first_seen_at, available_at을 구분하고, 모르는 최초 발표 시각을 만들어 넣지 않는다. 검색 API의 날짜 범위·조회 깊이 제한 때문에 과거 전체 뉴스의 완전한 수집원으로 사용하지 않는다. [S3, S4]

## 5 사건을 종목에 연결하는 방법

### 조회와 관련성 판단

기업 조회는 backend의 검증된 회사명과 별칭을 쓴다. corp_name, stock.name, 종목 사전의 정합성을 확인하며, 법인명·브랜드·우선주·자회사·이전 회사명을 무조건 같은 기업으로 합치지 않는다. 숫자 종목코드만 검색하지 않는다. frontend가 보낸 이름은 검색 권한이나 종목 확인의 근거로 삼지 않는다.

업종·시장·정책·국제 정세는 공통 사건 목록으로 조회하고 여러 종목이 재사용한다. 선택 종목과 보유·관심 종목의 사업 관계를 기준으로 필요한 범위를 선택한다. 화면 이동마다 모든 종목에 같은 국제 뉴스를 반복 요청하지 않는다. 첫 버전은 관리 가능한 사건 분류와 검색어 사전을 사용하고, 복잡한 자동 탐색은 실제 누락 사례를 근거로 추가한다.

각 연결에는 회사 또는 업종, 관계 종류, 근거 문서, 정보 기준일, 영향 경로, 연결 확실성을 보관한다. 예를 들어 “수출 제한 검토 → 해당 품목 포함 여부 → 이 회사의 해당 제품 판매 → 매출 영향 가능성”을 기록한다. AI가 고객사·매출 비중·해외 공장·거래 관계를 임의 생성해서는 안 된다.

### 심리와 관심의 분석

기사에서 관찰한 기대·우려와 실제 대중 전체의 심리는 구분한다. 언론 표현만 사용했다면 내부 증거 유형을 media_sentiment로 기록한다. 거래량·가격 반응은 관찰 자료이며 심리의 직접 측정값으로 단정하지 않는다.

기사 수는 동일 사건의 전재를 정리하고, 동일 출처 범위와 시간 구간의 평소 수준에 비교한다. 네이버 검색 total이나 임의의 최신 10건을 시장 전체 관심의 정확한 지표로 사용하지 않는다. 공개 반응·검색량 등 보조 자료가 없으면 “대중 심리가 개선됐다”는 문구를 생성하지 않는다.

소문, 검토 단계, 공식 확정, 시행, 정정·철회를 다른 상태로 관리한다. 공식 확정과 반복 보도는 별개다. 자극적인 제목이나 기사 수만으로 예측의 확신을 높이지 않는다.

### 관련 종목과 사건 묶음

선택 종목 화면은 해당 종목을 중심으로 보여준다. 내 종목 관리에서는 보유, 관심 순으로 정렬하되 같은 기준의 예측을 사용한다. 미보유 관련 종목도 분석 대상이며 기본 화면에서는 근거가 분명한 종목 최대 3개를 제안한다. 전체 시장 순위나 Scanner 점수는 변경하지 않는다.

분석이 허용된 자료에서는 동일 사건의 기사 묶음을 만들고 최초 보고, 후속 보도, 정정 이력을 연결한다. URL과 제목 중복 제거는 기사 중복 방지이고, 사건 묶음은 별도 단계다. 숫자·부정 표현·날짜가 바뀐 기사를 제목이 비슷하다는 이유로 삭제하지 않는다.

여러 뉴스가 충돌하면 종목별 동일 기간의 예상은 하나로 종합한다. 기사마다 서로 반대인 주가 예측을 나열하고 사용자에게 선택을 맡기지 않는다. 단, 충분한 근거가 없으면 충돌 이유를 밝히고 방향 판단을 유보한다.

## 6 과거 사례 분석과 데이터 구조

### 과거 자료의 보관

뉴스 표시용 메모리 캐시와 분석용 과거 자료를 분리한다. 과거 비교에는 필요한 기간의 보관·분석 권한이 있는 사건 기록, 당시 이용 가능했던 기업 관계, 수정 이력이 있는 가격 자료가 필요하다. 원문을 보관하지 않아도 제목·요약·임베딩·파생 특징의 보관 조건을 각각 지켜야 한다.

분석용 데이터는 event_id, source_ref, event_type, event_state, event_time, available_at, affected_entities, evidence_refs, feature_version을 기록한다. 가격은 종목·거래소·거래일, 가격 기준, 수정 주가 기준, 거래정지·상장폐지·결측 여부를 포함한다. 종목코드 변경과 상장폐지 종목을 제외해 유리한 결과만 남기지 않는다.

### 유사 사례의 선택

문장 유사도만으로 사례를 고르지 않는다. 사건 종류, 확정 수준, 규모, 기업 사업 구조, 발표 전 주가와 거래량, 시장 상황을 비교한다. 같은 회사의 사례가 충분하지 않으면 같은 업종으로 넓히며 그 사실을 기록한다. 수익률을 먼저 본 후 유리한 사례를 선택해서는 안 된다.

국제 사건은 “분쟁” 같은 큰 이름보다 원유 공급 감소, 수출 차단, 물류비 증가, 시장 전체 불안 등 실제 전달 경로를 비교한다. 정책은 발표·통과·시행을 구분하고, 미리 예고된 발표와 예상 밖 변경을 가능한 근거 범위에서 구분한다.

### 발표 후 반응과 지금부터의 예측

과거 사건 발생 후의 관찰 수익률과 현재 시점 이후의 예측 수익률을 별도 데이터로 관리한다. 이미 상승한 가격을 다룬 후속 기사에 그 상승을 예측 성과로 붙이지 않는다. 당시 실제 확보할 수 없었던 기사나 나중에 수정된 내용을 과거 입력에 넣지 않는다.

과거 사건 반응은 원칙적으로 사건 직전 확정 종가와 이후 1·5·20거래일 종가를 비교한다. 장중 사건에서 일봉만 있으면 발표 전 당일 움직임이 섞인다는 한계를 기록하며, 순수한 뉴스 효과나 거래 가능한 수익으로 표시하지 않는다. 정확한 분리에는 발표 시각과 당시 가격 자료가 필요하다.

예측 검증은 7장의 forecast_as_of와 reference_price로 별도 정렬한다. 수익률은 방향 예측에 사용하는 실제 종목 가격 변화와 시장·업종 대비 변화량을 구분한다. 시장 대비 초과 성과를 실제 주가 상승 확률처럼 표시하지 않는다.

주식 분할·병합 등 가격의 기계적 변화를 조정하고, 배당 포함 여부를 데이터셋에 명시한다. 거래정지·휴장·미도래 기간은 누락 상태로 처리하며 0%로 채우지 않는다. 거래일과 한국시간을 일관되게 적용한다.

### 통계와 해석

독립 사건 수, 대상 종목 수, 비교 기간, 상승·하락·보합 건수, 수익률 중앙값, 분포와 불확실성 구간을 내부 보고서에 포함한다. 같은 국제 사건에 노출된 여러 종목을 서로 완전히 독립인 사례처럼 세지 않는다. 다른 실적·공시·시장 사건이 겹친 경우를 표시한다. 관찰된 동반 움직임을 인과관계로 단정하지 않는다. [S5]

## 7 주가 방향 예측 계약

### 첫 예측의 목표와 시점

첫 공개 예측은 일봉 기준 다음 5거래일의 종목 가격 방향을 대상으로 한다. 1거래일과 20거래일은 내부 비교 지표로 먼저 검증하고, 검증된 기간만 화면에 추가한다. “단기”만 쓰지 않고 거래일 수를 표시한다.

MVP는 마지막으로 완전히 확보한 거래일 종가를 reference_price로 사용한다. 가격·뉴스·기업 관계의 기준 시각을 함께 기록한다. 동일 거래일 장중에 미래 종가가 필요한 입력을 쓰지 않는다. 새 뉴스는 해당 자료의 available_at 이후에만 반영하고, 장중 가격을 사용하지 않는 버전은 기준 종가 시점을 화면에 명시한다.

예측 수익률은 reference_price 대비 정해진 5번째 미래 거래일 종가의 변화다. 예측 발행은 기준 가격 확정 후부터 다음 거래일 시작 전까지의 정해진 창에서 수행하는 방식을 우선한다. 창 밖에서 중요한 새 사건이 발생하면 기존 예측을 오래된 상태로 표시하고, 새 기준 가격을 확보해 갱신한다. 이 가격 변화 예측을 실제 체결 가능한 매매 수익률로 표시하지 않는다.

| 내부 상태 | 사용자 문구 | 처리 기준 |
| --- | --- | --- |
| UP | 다음 5거래일 상승 가능성이 우세합니다 | 검증된 모델과 방향 출력 기준 충족 |
| DOWN | 다음 5거래일 하락 가능성이 우세합니다 | 검증된 모델과 방향 출력 기준 충족 |
| FLAT | 다음 5거래일 큰 가격 변화는 제한적일 것으로 예상합니다 | 미리 정한 가격 범위 안에 머무를 가능성이 우세 |
| ABSTAIN | 현재 자료로는 방향을 판단하기 어렵습니다 | 근거 부족, 충돌, 범위 밖 사건, 오래된 가격 등 |

보합 범위의 초기 연구 제안은 5거래일 수익률 ±1%다. 이 값은 검증된 시장 법칙이 아니며, 연구 시작 전에 데이터 변동성과 목적에 맞게 확정하고 holdout 결과를 본 후 변경하지 않는다. 사용자 문구가 뜻하는 가격 범위와 모델의 학습 기준은 동일해야 한다.

### 예측 계산과 문장 생성

모델 입력은 사건의 특성, 기업 연결 관계, 발표 전 가격·거래량, 이미 관측된 반응, 업종·시장 상태로 구성한다. 기사 감성 점수만으로 방향을 정하지 않는다. 처음에는 재현 가능한 통계 모델을 사용하고, 단순한 가격 기반 모델과 과거 사건 빈도 기준보다 나은지 비교한다.

AI 언어 모델은 허용된 자료의 정보 추출과 설명 작성에 사용한다. 방향·확률·사례 수·가격은 검증된 계산 결과를 전달받아 표현한다. 모델이 스스로 확률이나 과거 성과를 만들어 내지 못하게 구조화된 출력과 수치 검사를 적용한다. 기사 안의 지시는 데이터로 취급하며 시스템 동작을 바꾸지 못하게 한다.

종목별 동일 기간 예측은 여러 사건을 함께 반영해 한 번 생성한다. 사건 간 독립성을 가정해 확률을 단순 평균·합산하지 않는다. 개별 기사의 이유를 전체 가격 움직임의 확정 원인처럼 서술하지 않는다.

현재 가격이 이미 반응했다는 사실은 계산할 수 있지만, 정보가 전부 반영됐는지는 직접 확인할 수 없다. “이미 반영이 끝났습니다” 대신 근거에 맞춰 “발표 이후 상승 폭이 커 추가 상승 여력이 제한적일 수 있습니다”처럼 쓴다.

## 8 예측 검증과 공개 조건

### 검증 방식

학습, 모델 선택, 최종 평가를 시간 순서대로 분리한다. 같은 사건과 전재 기사, 같은 국제 사건에 연결된 여러 종목은 데이터 분할을 넘나들지 않게 묶는다. 평가 기간과 겹치는 결과 관찰 구간은 제외한다. 가장 긴 20거래일 결과를 사용하면 그 기간에 맞는 간격을 둔다.

과거 기사는 당시 이용 가능했던 버전만 사용한다. 지금의 기업 사업 구성으로 과거 관련성을 재작성하지 않는다. 언어 모델이 학습 중 알게 된 이후 결과를 과거 판단에 섞는 문제도 점검하며, 최종 평가는 모델 확정 이후 새로 축적한 자료에서 다시 확인한다. [S6]

정확도 하나로 출시 여부를 판단하지 않는다. 상승·하락·보합별 성능, 예측을 제공한 비율, 판단 유보 비율, 확률의 정확성, 업종·사건 종류별 차이를 기록한다. 항상 상승이라고 하는 기준, 뉴스 없는 가격 모델, 과거 사건 단순 빈도와 같은 기간·같은 대상에서 비교한다.

### 초기 공개 기준 제안

아래 수치는 구현자가 임의로 성능을 주장하지 않도록 정한 시작 기준이다. 데이터 확보 후 실험 계획서에 확정하고, 최종 평가 결과를 확인한 다음 유리하게 낮추지 않는다.

- 평가 표본은 최소 200개의 독립 사건 묶음을 목표로 하고, 출력하려는 방향별 실제 결과가 최소 30건 이상 있어야 한다. 동일 거시 사건의 여러 종목은 표본 수를 부풀리지 않는다.
- 같은 출력 대상에서 뉴스 없는 기준 모델보다 확률 오차가 개선돼야 한다. 사건별 묶음을 유지한 95% 불확실성 구간에서도 개선이 확인되는지 보고한다.
- 확률을 숫자로 공개하려면 예측 확률 구간별 실제 빈도를 검증한다. 평가 표본 30건 이상인 구간에서 차이가 10%p를 넘으면 해당 구간의 확률 공개를 보류한다.
- 방향 공개의 초기 후보 기준은 보정된 최대 확률 0.60 이상이다. 이는 성능 보장이 아니며, 별도 검증 조건을 함께 충족해야 한다. 화면에는 숫자 확률보다 방향과 근거를 우선한다.
- 판단 유보로 성능을 높여 보이지 않도록 전체 대상 대비 예측 제공 비율을 보고한다. 초기 목표는 10% 이상이며, 일부 업종·사건에만 통과하면 그 범위만 공개한다.
- 모델을 고정한 뒤 최소 20거래일 동안 새 자료로 비공개 검증을 진행하고, 모든 평가 대상의 5거래일 결과가 성숙한 후 비교한다. 이 기간은 최소 관찰 기간이며 표본 요건을 대체하지 않는다.

기준을 충족하지 못하면 READY를 반환하지 않는다. 뉴스 표시는 계속 가능하지만 예측은 INSUFFICIENT_EVIDENCE 또는 MODEL_NOT_VALIDATED로 표시하고, 전체 예측 기능은 미완료로 보고한다. 가짜 데이터나 mock 결과로 실제 예측 화면을 운영하지 않는다.

### 운영 중 예측의 수명

forecast_id, generated_at, forecast_as_of, model_version, data_version, expires_at을 기록한다. 중요한 정정·철회·신규 사건, 오래된 가격, 기업 관계 변경이 발생하면 기존 예측을 취소하거나 새 버전을 발행한다. 과거 예측을 덮어써 성과 기록을 바꾸지 않는다.

데이터 누락, 예측 제공 비율 급변, 방향 쏠림, 실제 성과 저하를 관찰한다. 이상이 생기면 해당 범위의 예측 공개를 중단하고 뉴스 목록과 기존 종목 분석은 유지한다. 검증 가능한 자료가 없는 극단적 사건에서는 억지로 유사 사례를 붙이지 않는다.

## 9 Backend 구조와 데이터 경계

### 권장 모듈 구성

기존 프로젝트 관례를 확인한 뒤 다음 책임 분리를 적용한다. 파일 이름은 제안이며 책임과 의존 경계는 필수다.

```text
backend/app/news/
  models.py          # 표시용 뉴스와 권한 메타데이터
  naver.py           # 인증, HTTP, validation, 표시 정리, 오류 변환
  service.py         # 회사명 결정, 조회 범위, 캐시, 결과 구성
  policy.py          # source별 허용 작업과 보관 정책
backend/app/news_analysis/
  events.py          # 허용된 자료의 사건 추출 및 버전 관리
  relevance.py       # 기업, 업종, 국가, 정책 관계 연결
  history.py         # 과거 사례와 시점이 일치하는 가격 비교
  forecast.py        # 검증된 예측 모델 적용과 판단 유보
  explanation.py     # 계산 결과를 쉬운 문장으로 작성
backend/app/api/
  news.py            # 독립 뉴스 및 예측 API
```

NEWS.1에서는 필요한 최소 파일만 만든다. 후속 분석 모듈은 해당 단계에서 구현한다. data_sources.py 안에 외부 HTTP 로직을 추가하지 않는다. 시장 데이터와 기업 사전은 공통 서비스를 통해 재사용하고, 예측 서비스가 Strategy 결과를 직접 수정하지 않게 한다.

### 세 가지 내부 모델

| 모델 | 핵심 필드 |
| --- | --- |
| NewsItem | id, title, description, url, source_url, source_name, source_domain, provider, published_at, timestamp_kind, query, fetched_at |
| NewsEvent | event_id, event_type, scope, state, entities, available_at, event_time, source_refs, evidence_refs, rights_policy_id, version |
| StockNewsForecast | forecast_id, code, market, horizon_sessions, status, direction, reference_price, price_as_of, forecast_as_of, generated_at, expires_at, reasons, model_version, data_version |

NewsItem은 Naver 원본 전체를 그대로 frontend에 넘기지 않는다. originallink를 유효성 검사한 뒤 원문 url로 우선 사용하고, 없으면 유효한 제공 링크를 사용한다. source_url은 provider가 제공한 링크로 의미를 고정한다. source_name은 확인된 값만 제공하며 도메인만으로 임의 언론사명을 추정하지 않는다.

HTTP 또는 HTTPS URL만 허용한다. javascript·data URL과 잘못된 링크를 버리고, 서버가 원문을 자동 방문하지 않게 한다. canonical URL 처리는 알려진 추적 파라미터만 제거하며 기사 식별 파라미터를 보존한다. ID는 정리된 출처와 기사 식별자로 안정적으로 생성한다.

표시 과정의 HTML 강조와 entity를 안전한 텍스트로 처리하되 원문 의미를 바꾸지 않는다. frontend는 HTML을 삽입하지 않는다. 문법상 잘못된 항목은 개별 제외하고, 응답 구조 전체가 잘못됐으면 provider 실패로 처리한다. 손상된 응답을 정상 0건으로 숨기지 않는다.

예측 내부 확률·특징·상세 비교 자료는 접근 통제된 검증 데이터로 유지한다. 사용자 API에는 검증된 최소 정보만 노출한다. Secret, 원본 인증 헤더, 불필요한 기사 원문, 보유 수량·계좌 식별자를 외부 뉴스 서비스나 설명 모델에 전송하지 않는다.

## 10 API와 오류 계약

### 공개 경로

| 경로 | 계약 |
| --- | --- |
| GET /api/stocks/{code}/news | market과 limit을 받는다. limit은 1~10, 기본 10이다. 조회 기업명은 backend에서 확인한다. |
| GET /api/stocks/{code}/news-insights | 종목별 종합 예측과 관련 사건을 반환한다. 초기 horizon은 5거래일로 제한한다. |
| GET /api/news/insights | 후속 내 종목 화면용이다. 기존 인증 문맥에서 보유·관심 종목을 결정하고 다른 사용자의 종목을 노출하지 않는다. |
| GET /api/providers/status | naver_news의 configured, provider_kind, role을 반환한다. configured는 값 존재 여부이며 인증 성공을 뜻하지 않는다. |

종목 검증은 기존 normalize_stock_code와 시장 허용 목록을 재사용한다. 없는 종목은 STOCK_NOT_FOUND로 구분한다. 임의 회사명·URL을 받는 자유 검색·프록시 API는 만들지 않는다.

### 뉴스 응답 예시

아래 값은 API 형식 예시다. fetched_at은 마지막 성공 수집 시각이며 캐시 응답 때 현재 시각으로 바꾸지 않는다. count는 반환 items의 길이다.

```json
{
  "code": "005930", "market": "KOSPI", "company_name": "삼성전자",
  "query": "삼성전자", "fetched_at": "2026-09-25T09:00:00+09:00",
  "status": "ok", "items": [], "count": 0,
  "cache": {"hit": false, "stale": false}
}
```

예측 응답은 status=READY, ABSTAIN, INSUFFICIENT_EVIDENCE, MODEL_NOT_VALIDATED, DATA_STALE, FAILED 중 하나를 사용한다. READY인 경우 direction=UP, DOWN, FLAT과 horizon_sessions=5, 기준 가격·시각, 한 줄 결론과 최대 2개 이유를 제공한다. 그 외에는 direction과 공개 확률을 null로 하고 reason_code와 짧은 설명을 제공한다. ABSTAIN은 유효한 계산 결과의 판단 유보이며 HTTP 실패가 아니다.

### 오류와 부분 실패

| 오류 코드 | HTTP | 처리 |
| --- | --- | --- |
| NEWS_NOT_CONFIGURED | 503 | 키 미설정 또는 공백. 재시도 반복 금지 |
| NEWS_AUTH_FAILED | 502 | upstream 401·403. 사용자 로그인 실패와 구분 |
| NEWS_RATE_LIMITED | 503 | upstream 429. retry_after 제공, 즉시 재시도 금지 |
| NEWS_QUERY_INVALID | 400 | 유효한 회사명·조회 조건 확보 실패 |
| NEWS_PROVIDER_FAILED | 502 | upstream 5xx, 응답 구조 오류, 연결 오류 |
| NEWS_TIMEOUT | 504 | 제한 시간 초과 |
| NEWS_USAGE_NOT_ALLOWED | 503 | 요청한 활용을 허용할 source가 없음 |

자체 호출 제한은 HTTP 429다. 오류 본문은 error.code, message, retryable, retry_after, request_id로 통일하며 원본 오류·Secret을 제외한다. 기존 asJson을 구조화 오류와 호환되게 수정한다. 일부 provider만 실패하면 가능한 결과와 partial 상태를 반환한다.

## 11 환경변수 캐시와 화면 상태

### 인증과 설정

project-root .env에 NAVER_NEWS_CLIENT_ID와 NAVER_NEWS_CLIENT_SECRET을 두고, Settings에 naver_news_client_id: str | None = None 및 naver_news_client_secret: str | None = None을 추가한다. .env.example에는 동일 이름의 빈 값만 둔다. dotenv 파일 경로는 기존 project-root 설정을 유지한다. frontend VITE_*로 전달하지 않는다.

기존 NAVER_CLIENT_*가 실제 .env에 있으면 값을 출력하지 않고 새 이름으로 옮기며, 서로 다른 두 값이 있으면 임의 선택하지 않는다. 구 이름을 영구 fallback으로 남겨 혼란을 만들지 않는다. 이 이전은 실제 파일과 사용처를 확인한 뒤 수행한다. 비어 있거나 공백뿐인 값은 configured=false다.

provider_kind는 developer_center 또는 api_hub로 명시한다. 개발자센터는 X-Naver-Client-Id 및 X-Naver-Client-Secret, API HUB는 X-NCP-APIGW-API-KEY-ID 및 X-NCP-APIGW-API-KEY를 사용한다. 기본 URL은 코드의 허용 목록으로 제한한다. 동일 Secret을 여러 호스트에 시도하지 않는다. [S3, S4]

### 캐시와 외부 호출

source 계약에서 해당 목적의 서버 캐시가 허용된 경우에만 TTL 기본 5분을 적용한다. 최대 항목 수는 초기 256개로 제한한다. 키에는 provider, 권한 정책 버전, 정규화한 query, sort, 언어, 조회 크기를 포함한다. 기본 10건을 같은 정책으로 캐시하고 화면의 5건 표시는 frontend에서 처리한다.

동일 query의 동시 요청은 하나의 외부 호출을 공유한다. 빈 정상 결과도 짧게 캐시한다. 인증 실패는 정상 결과로 캐시하지 않고 재호출 폭주를 막는다. 만료 자료는 접근 시와 정리 작업에서 실제 제거하며, 만료 후 사용도 source의 허용 범위 안에서만 한다. 프로세스별 메모리 캐시라는 제한을 기록하고 다중 worker에서 공유된다고 가정하지 않는다.

새로고침은 provider 호출을 보장하는 버튼이 아니다. 정상 최신 캐시는 재사용하며 강제 새로고침은 같은 query당 최소 60초 간격으로 제한한다. 연결·읽기 timeout을 설정하고, 네트워크 오류나 일부 5xx만 최대 1회 지연 재시도한다. 401·403과 잘못된 query를 자동 재시도하지 않는다. 429는 제공된 대기 시간을 존중한다.

조회량은 source별 일일 한도와 설정된 예산으로 관리한다. 화면을 열지 않았는데 전체 종목을 반복 조회하는 작업은 만들지 않는다. 허용된 과거 사건 수집과 예측 검증 작업은 별도 실행 경로와 예산을 사용한다.

### Frontend와 오류 격리

frontend/src/services/api.ts에 StockNewsItem, StockNewsResponse, fetchStockNews를 추가하고 후속 StockNewsForecast 및 fetchStockNewsInsights를 분리한다. 데이터 키는 market과 code를 포함한다. 종목 변경 즉시 이전 표시를 지우고 loading 상태로 바꾸며, AbortController와 요청 식별자를 함께 사용해 늦은 응답을 무시한다.

뉴스는 stock context 전체 성공을 기다리지 않는다. backend 종목 사전에서 이름을 검증할 수 있으면 DART 장애 중에도 조회한다. 식별이 불가능하면 종목 식별 실패만 표시하고 선택된 다른 종목의 이름을 재사용하지 않는다.

뉴스 오류는 “최근 뉴스를 불러오지 못했습니다”로 표시한다. 예측만 실패하면 뉴스 목록은 유지하고 “현재 주가 예측을 제공할 수 없습니다”와 짧은 이유를 표시한다. 뉴스 없음, 예측 근거 부족, 설정 누락, 장애를 같은 빈 화면으로 처리하지 않는다. 기존 Strategy 결과를 지우는 setter를 뉴스 오류 처리에서 호출하지 않는다.

## 12 테스트와 운영 확인

CI에는 실제 Secret을 넣지 않는다. provider는 mock transport, 시각은 조작 가능한 clock, 예측은 고정된 합성 fixture를 사용한다. 합성 자료는 테스트·개발 화면에서만 사용하고 실제 종목의 검증 결과로 배포하지 않는다.

| 검증 영역 | 필수 시나리오와 기대 결과 |
| --- | --- |
| 인증과 설정 | 키 없음·한쪽 누락·공백은 미설정. 플랫폼별 헤더와 host 정확. 실제 값·인증 헤더가 응답, 예외, 로그에 없음 |
| 조회와 파싱 | 검증된 회사명 query, sort=date, limit 범위, HTML 태그·entity 처리, timezone, 빈 설명·원문 링크 누락·깨진 날짜 처리 |
| 데이터 안전성 | 위험 URL 제외, HTML 삽입 없음, 원문 자동 수집 없음, malformed 항목과 전체 응답 오류 구분 |
| 중복과 캐시 | 허용된 중복 정리, 정정·숫자·부정 표현 보존, TTL 만료, 동일 query hit, 동시 요청 1회, limit·provider 충돌 없음 |
| 오류 | 401·403, 429, 5xx, timeout, 연결 실패를 계약대로 변환. 무한 retry 없음. 제한된 source의 AI·저장 경로 차단 |
| 종목 관련성 | 회사명 없는 정책 뉴스도 근거가 있으면 연결. 같은 업종이라는 이유만으로 확정 연결하지 않음. 관계 기준일 보존 |
| 심리 | 전재 기사로 관심 증가 부풀림 없음. 소문과 확정 구분. 미관측 대중 심리·거래 관계 생성 없음 |
| 과거 사례 | 시간 역전·미래 자료·재전재 중복·상장폐지 누락·분할 오류·휴장·거래정지·결과 미도래 처리 |
| 예측 | 같은 입력과 버전은 재현 가능. 기간·기준 가격 정확. raw return과 시장 대비 성과 구분. 미검증 모델 READY 금지 |

문자열 검사는 “최근 뉴스”, fetchStockNews, 새 탭 속성, VITE_NAVER_* 부재를 확인하는 보조 수단이다. 실제 값이 frontend bundle에 포함되지 않는지와 독립 오류 처리는 행동 테스트로 검증한다. 정적 문자열 검사만으로 완료 처리하지 않는다.

Frontend Node 22 build와 필요한 테스트, Backend Python 3.11·3.14 전체 필수 테스트를 통과시킨다. 실패하면 GitHub 로그에서 원인을 확인하고 수정 후 다시 실행한다. 관련 없는 회귀 실패도 설명 없이 무시하지 않는다.

로컬 실제 연결은 CI 통과 후 1회 수행한다. git pull과 run-dev.ps1 실행 후 삼성전자 등 한 종목을 선택해 원문 링크·시각·뉴스 표시·호출 횟수를 확인한다. 새로고침과 재진입은 캐시를 사용하도록 해 불필요한 live 요청을 만들지 않는다. 실제 검증 성공 여부와 확인 시각을 기록하되 키·헤더·민감한 응답 로그는 남기지 않는다.

관측 지표는 provider 호출 수·지연·오류 코드·캐시 hit·버린 항목 수·관련성 미확정 비율·예측 제공 비율이다. Secret이나 제한된 기사 본문을 운영 로그에 기록하지 않는다. configured 상태를 live 인증 검증으로 보고하지 않는다.

## 14 인수 기준과 다음 채팅 전달문

### 최종 인수 기준

- 사용자는 첫 화면에서 대상 종목, 예상 주가 방향, 기간, 핵심 이유를 파악할 수 있다. 주가 예측 대신 사업 영향 설명만 있으면 전체 요구를 충족하지 못한다.
- 기업명 없는 업종·정책·국제 뉴스도 근거에 따라 연결한다. 계약·실적 종류에만 한정하거나 보유 종목만 분석하면 미완료다.
- 공식 확정, 기대·우려, 소문, 관찰된 가격 반응을 구분한다. 종목마다 다른 영향을 설명할 수 있다.
- 원문은 새 탭 링크로 제공한다. 기사 전체 수집·복제·펼쳐보기 없이 제목과 짧은 내용으로 구성한다.
- 예측이 충분히 검증된 범위만 공개한다. 판단 유보, 오래된 데이터, 미검증 모델을 구분하고 가짜 확률·사례를 사용하지 않는다.
- 과거 비교는 같은 사건을 중복 집계하지 않고 당시 알 수 있던 자료를 사용한다. 기준 시각, 거래일, 가격 조정, 시장 움직임을 일관되게 처리한다.
- 말투는 담백한 설명체다. 가볍거나 가르치는 문구, 전문용어 나열, 긴 해설을 첫 화면에 넣지 않는다.
- Secret은 backend에만 있고 API·로그·frontend bundle에 노출되지 않는다. provider 플랫폼과 권한 정책이 확인돼 있다.
- 뉴스와 예측이 실패해도 종목 분석을 유지한다. 기존 Strategy·Scanner·Ranking·Risk 점수와 자동 매매 동작을 임의로 변경하지 않는다.
- CI 3개 환경의 통과, 실제 API 1회 확인, 예측 검증 보고서, 최종 UI 확인을 단계별 증거로 남긴다.
